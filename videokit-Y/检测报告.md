## 结论

没有发现可以被远程直接利用的严重漏洞。Electron 主进程和 IPC 的基础防护做得不错。但有三处中等风险值得修：绿色版自动更新不校验文件；macOS 达芬奇脚本放在多用户共享目录；多数 API 密钥明文保存。

## 核对通过的部分

| 项目 | 结果 |
|---|---|
| 主窗口 | `nodeIntegration: false`、`contextIsolation: true`、`webSecurity: true`；拦截页面跳转；新窗口只能用系统浏览器打开 http/https 链接 |
| IPC 接口 | 44 个接口统一经过 `handleTrusted`，按发送方页面地址白名单校验（`electron/services/trustedRenderer.js`） |

## 发现的问题

### 1. 【中】绿色版自动更新不校验下载的文件

`electron/updater.js` 的 `portableUpdate()` 从 GitHub Release 下载 zip 后，直接解压覆盖程序目录（第 316–318 行），中间没有核对 SHA-256，也没有验证构建来源证明。

`SECURITY.md` 说发布包带有 SHA-256 校验和来源证明，但这只对手动验证有用，自动更新并没有用上。目前完全依赖 HTTPS 和 GitHub 本身：GitHub 账号或仓库一旦被盗，所有绿色版用户会自动装上被篡改的版本。

建议：下载后先读取同一 Release 里的 `checksums.sha256` 核对，最好再验证来源证明，通过后再解压。

### 2. 【中】macOS 达芬奇菜单脚本会执行共享目录里的代码

`electron/services/davinciFusionExport.js` 的 `installResolveMenuScript()` 用**管理员权限**往系统目录 `/Library/.../Fusion/Scripts/Comp/` 装了一个启动脚本。这个脚本每次运行时，都会执行 `/Users/Shared/VideoKit/Resolve/VideoKit Import Fusion Latest.py`。

`/Users/Shared` 是 Mac 上所有用户都能写入的目录。在多人共用的 Mac 上，另一个用户只要抢先建好这个目录和文件，任何人在达芬奇里点这个菜单，都会以自己的身份运行那个人的代码。

建议：把要执行的脚本放在当前用户自己的目录里；或者执行前检查文件属主是不是当前用户、有没有被其他人改写的权限。

### 3. 【中】多数 API 密钥明文保存

`electron/services/settings.js` 里，Gemini 密钥（`gemini_keys.json`）、ElevenLabs 密钥，以及 ElevenLabs 网页令牌（包括 authorization 和 cookie，见 `apiRouter.js:595`）都以明文 JSON 写在用户数据目录。只有 Gladia 用了 `safeStorage` 加密。

电脑上的任何程序、备份或同步工具都能直接读到这些密钥。ElevenLabs 的 cookie 等于登录状态。

建议：都改用 `safeStorage` 加密，和 Gladia 一样。

### 4. 【低】`local-media://` 可读取全盘任意同类文件，主界面没有 CSP

`electron/main.js:783` 的 `local-media` 协议只按后缀放行（包括 `.json`、`.txt`、`.xml`、`.zip`），不限制目录。主界面 `src/index.html` 也没有设置内容安全策略（CSP）。

目前没发现能利用的 XSS，外部网站也访问不到这个协议。但界面里只要出现一处 XSS，就能读到磁盘上的密钥文件（见第 3 条）。

建议：限制只能读取用户选择的素材目录和输出目录；给主界面加 CSP。

### 5. 【低】后台渲染窗口关闭了全部隔离

`electron/main.js:1270` 的后台渲染窗口开着 `nodeIntegration: true`，关闭了 `contextIsolation` 和 `webSecurity`。它现在只加载本地脚本，抽查没发现往页面里插入外部 HTML 的地方，所以风险低。但这个窗口里一旦混进外部内容（例如导入别人分享的预设包），就等于能完全控制电脑。

建议：改用 preload 只暴露需要的接口，打开 `contextIsolation`。

### 6. 【低】yt-dlp 的网址参数前没有加 `--`

`electron/services/ytdlp.js` 第 274 行和第 318 行把网址直接追加到参数末尾，前面没有 `--` 分隔。如果“网址”以 `-` 开头（比如粘贴了奇怪的文本，或者播放列表里某个条目被构造过），yt-dlp 会把它当成选项，例如 `--exec=...` 就能执行命令。

建议：在网址前加一个 `'--'`。

### 7. 【低】Windows 发布构建下载的组件没有校验、版本不固定

`.github/workflows/release-windows.yml` 构建 Windows 版时：
- 下载 Python 嵌入包和 `get-pip.py`，都没有校验哈希；
- `yt-dlp`、`requests` 不固定版本；
- FFmpeg 用的是 `latest` 的 master 每日构建，也不校验。

结果是每次构建内容都可能不同，上游被篡改时也发现不了。建议锁定版本并核对 SHA-256。macOS 版做得对：`scripts/prepare-macos-runtime.cjs` 按 `macos-runtime-assets.json` 里的 SHA-256 校验了 Python 和 FFmpeg，可以照这个改 Windows。

### 8. 【低】Wav2Lip 加载模型允许执行任意代码

`vendor/wav2lip/inference_api.py:85` 用 `torch.load(..., weights_only=False)` 加载模型。加载来路不明的 `.pth` 文件会执行其中的任意代码，只能用官方模型。

### 9. 【提示】其他

- `backend/server.py` 是旧的 Python 后端，已经不再启动，也不会打进安装包。但它的 CORS 允许任何网站带凭据访问，如果有人手动运行，任何网页都能调用它。建议删除。
- 根目录有个内容只有 `1` 的文件 `1`，像是误提交。
- `package.json` 里作者邮箱是占位的 `videokit@example.com`。
- 仓库根目录没有 LICENSE 文件。

## 微软语音（Edge TTS）专项

涉及文件：`electron/services/edgeTts.js`、`electron/services/edge_tts_bridge.py`、`src/microsoft-tts.js`、`electron/services/workflow.js`、`setup-edge-tts.cmd`、`requirements-edge.txt`。

**工作方式：** Node 启动内置 Python，运行 `edge_tts_bridge.py`，通过标准输入传 JSON 参数。Python 用 `edge-tts` 库连接微软 Edge“大声朗读”的在线服务生成 MP3 和字幕，再把结果交回 Node。

### 安全方面：没有发现问题

| 项目 | 结果 |
|---|---|
| 启动 Python | 用参数数组调用，不经过 shell；参数通过标准输入传 JSON，不拼命令行 |
| 音色名 | 校验格式（例如 `zh-CN-XiaoxiaoNeural`），乱填的值会被拒绝 |
| 语速 | 校验为 `-100%` 到 `+100%` |
| 输出文件 | 写到程序的安全临时目录，文件名是随机 UUID，读取后立刻删除 |
| 界面显示 | 微软返回的音色名、错误信息都用 `textContent` 显示，没有 XSS |
| 依赖 | `edge-tts==7.2.8` 固定版本，另外给 `multidict` 设了安全版本下限 |
| 打包 | Windows 和 macOS 正式版都把 `edge-tts` 装进了内置 Python，用户不需要另外安装 |

### 需要注意的地方

1. **【风险】用的不是微软官方付费接口。** `edge-tts` 调用的是 Edge 浏览器“大声朗读”功能背后的服务，不需要密钥，但这不是微软对外开放的 API：
   - 微软随时可能改验证方式或限制调用，届时配音会直接失败，只能等 `edge-tts` 出新版、VideoKit 再发版。版本固定在 7.2.8，用户自己没法升级。
   - 微软没有授权把这个服务用于批量或商业视频制作。如果用它做商业内容，有违反服务条款的风险。需要稳定或商用的话，应该改用 Azure 语音服务（要密钥，按量计费）。
2. **【隐私】配音文案会发给微软服务器。** 这是在线服务的必然结果，介意的话需要在界面上提示用户。
3. **【小问题】出错提示指向一个安装版里没有的文件。** 内置 Python 缺少依赖时，提示“请运行 setup-edge-tts.cmd”。但这个脚本只在源码目录里，不会打进安装包，而且只支持 Windows。安装版用户看到这条提示也没法照做，应改成“请重新安装 VideoKit”。
4. **【小问题】手动构建流程不带微软语音。** `.github/workflows/build.yml`（手动触发的那条构建）安装 Python 依赖时没装 `edge-tts`。用它构建出来的包，微软配音不能用。正式发版用的是 `release-windows.yml`，不受影响。
5. **【小问题】没有 Linux 支持。** 正式发版只构建 Windows 和 macOS。Linux 打包配置也没带内置 Python，从源码自己打 Linux 包的话，微软配音只能靠环境变量 `VIDEOKIT_EDGE_PYTHON` 手动指定 Python。
